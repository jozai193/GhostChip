# Five highest-risk technical assumptions

Ranked by likelihood × damage to the central product claim, not implementation inconvenience. Status is as of this architecture proof.

| Rank | Assumption and failure mode | Falsification experiment / acceptance gate | Mitigation and current evidence |
|---|---|---|---|
| 1 — Critical | A datasheet-derived model is a trustworthy oracle. An extractor may omit a condition, confuse “may” with “must”, or give the right citation for the wrong transition. A driver can then falsely PASS deterministically. | Independently review a gold set of at least three BME280 behaviors and two second-device behaviors. Include negative prose/ambiguous clauses and mismatched citations. Require no unsupported accepted rule and exact agreement on curated distinguishing traces. One accepted false semantic claim blocks broad “automatic verification” positioning. | The BME280 latch slice now has pinned pages, two citations, missing-clause and changed-layout tests, pending-by-default output and hash-bound review. This is one behavior, not the full fidelity gate; silicon fidelity remains untested. |
| 2 — Critical | Bus traffic contains enough information to judge driver intent, and tests are independent of the model. A staged update, deliberate no-op, or ignored request can be misclassified. | Hold model and scenario fixed; run correct, reversed, omitted, wrong-value and repeated-write variants. Both correct readback and incorrect effective state must be observable. A no-op must fail a nonzero request; a legitimate staged write must not fail before the completion checkpoint. | Keep intent/checkpoints in Scenario, not device rules; later map adapter function return to checkpoint. This proof exercises these mutations and separates stored/effective state. Scenario authorship is manual; independent application contracts remain necessary. |
| 3 — High | A compact generic IR can represent a second vendor's behavior without hidden device code. Timing, read side effects, ambiguity and banked addresses can force per-chip patches or silent approximations. | Represent ADXL345 selective read-clear and FIFO bypass flush from source, then execute one compiled driver scenario with the unchanged event kernel. Reject the generalization claim if runtime branches on device id/address or requires unsupported behavior to be ignored. | **Stage 3 passed for this bounded slice:** v1 represented both rules; the generic runtime has no ADXL identifiers; real-PDF, negative-extraction, runtime, compiled-C and rule-removal tests pass. This does not establish timing, burst, banking, or arbitrary-device generality. |
| 4 — High | An existing real driver can be adapted while preserving its behavior. C compilation alone does not prove MCU assumptions, SDK callbacks, burst transfers, delays or branch-dependent reads are faithfully represented. | Integrate one permissively licensed vendor/open-source driver through documented bus/delay callbacks. Make a returned read value change a real branch; test error propagation. Record adapter edits and compile/runtime assumptions. If most driver logic must be rewritten, narrow the compatibility claim. | The current original C fixture uses live synchronous HAL calls and checks returned ID/readback, but is not a full Bosch driver. GCC/WSL works. MCU instructions, threads/interrupts and timing are unsupported. |
| 5 — High | A public runner can safely and reproducibly execute uploaded C and maintain bounded resources. A container or timeout alone does not constrain compiler extensions, syscalls, filesystem/network access or process descendants. | Before arbitrary remote uploads, independently exercise compile-time file access, runtime egress, forks, hangs and output floods inside the actual deployment isolation. Require enforced filesystem/network/process limits and deterministic termination; otherwise block uploads. | Curated drivers only for a hosted demo. Current local subprocess has timeout/output/CPU/address-space/file-size limits and process-group cleanup, with tests for timeout and output flood. It is explicitly not an untrusted-code sandbox. |

The next investment should be risk 4 (an independently maintained permissively licensed driver) while expanding the independent gold set required by risk 1, not frontend polish. If that fails, an honest reviewed-model testing tool remains possible, but the broad driver-compatibility claim must be reduced.
